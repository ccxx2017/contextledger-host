## 1. inject vs pre-step：最小改动比较

| 维度 | 继续 inject（现实现） | 改用 pre-step 供给（本方案） |
|---|---|---|
| 改动量 | **零改动**（机制已跑通） | 重写 on 供给点 + 状态机 + mock 测试（约 100 行） |
| 供给时点 | 会话创建时一次性 splice 进 next-step 收件箱 | **每个步骤边界**决策是否追加（步骤边界的供给控制） |
| 版本变化响应 | 会话内不响应（inject 仅一次） | 下一个适用步骤即响应（revision 对比） |
| 压缩后响应 | 不响应 | 检测 compaction 后重新供给 |
| 重复累积风险 | 单次注入，无累积 | 状态机保证同版本不重复追加 |
| 接纳可观测 | 无（注入后成败不可知） | 可在瀑布返回值中按消息 ID 核对最终接纳 |
| 选型理由 | — | **步骤边界的供给控制**：供给决策需要"每步一判"的时点（首供/换版/压缩后），inject 的一次性时点无法承载该控制；**与"不持久化"无关**（该结论已撤回） |

## 2. 尝试（attempt）与接纳（acceptance）分离

定义：
- **尝试** = pre-step 瀑布中构造供给消息并拼入返回批次；
- **最终接纳** = 瀑布返回值（`downstream.messages`）中该消息（按本次生成的消息 ID）**仍然存在**——即后续监听器/宿主未将其剔除。这是步骤边界上可观测的最强接纳信号。

状态机（键 = `sessionId + "\u0000" + clProject`，会话与项目双维隔离）：

```
idle ──(首步/revision变化/压缩标记)──> attempt(rev, msgId)  ──> 下游含 msgId?
                                                                  ├─ 是 → accepted(rev)   [lastSuppliedRevision=rev]
                                                                  └─ 否 → attempt_failed  [状态不变，下一步重试]
accepted(rev) ──(revision又变)──> attempt(rev2,…)
accepted(rev) ──(compaction事件)──> needs_resupply ──(下一步)──> attempt(rev,…)
```

- `lastSuppliedRevision` **仅在接纳成立时**写入；尝试失败不更新（下步自动重试）。
- **恢复（resume）路径**：状态机存于插件内存——恢复会话后内存状态丢失 → 视同新会话（首步重新供给）。由于供给消息带 revision 且内容为完整快照，重复供给同一版本在恢复场景是**幂等安全**的（见 §3 版本权威规则）；副作用仅一条重复历史消息。此项的**真实恢复链路验证 = 未验证**（本轮预算外），已标记。
- **压缩完成路径**：监听 `session/event` 的 `compaction/*` 事件置 `needs_resupply`；**压缩后立即重试**由下一步的 pre-step 自然承担（无需定时器）。**真实压缩触发 = 未验证**（headless 短会话难以自然触发压缩；本地 mock 覆盖状态转换，见 §6）。
- 未覆盖、显式标记未验证：压缩后的实际供给 run、恢复会话的实际供给 run、多项目并行会话的真实隔离（mock 已覆盖逻辑层）。

## 3. 累积与版本语义（收紧表述）

- **同版本不重复追加 ≠ 旧版本已替换**。明确规则如下：
  1. **快照/增量**：供给消息为**完整快照**（renderMemory 渲染全部已发布状态 + revision 标注），非增量；无增量合并逻辑。
  2. **旧记录撤回**：**无主动撤回机制**。历史中的旧版本供给消息保留为历史记录，其正文自带 `revision=…` 标注与"非当前约定权威"规则文本。
  3. **版本权威规则**：**同一会话内，最后一次被接纳供给的 revision 为当前权威**；更早的供给消息视为被替代的历史证据。该权威仅在本插件与记忆文本内声明，不改变 DSH 任何机制。
  4. **体积边界**：渲染后记忆文本 > 8192 字符时截断并显式标记 `degraded:memory_truncated`（状态行 + 旁证），不静默截断。
- **版本替代测试必须包含冲突与删除变化**（本方案验证 run V2 的夹具要求）：
  - 冲突变化：同一实体 state_slot 的新值覆盖旧值（如 impl-owner 二次改派）；
  - 删除变化：某实体状态从快照中**消失**（发布内容不再含它）——验证模型侧"消失即不再为当前约定"的可观察行为。

## 4. 请求证据链（不预设 derived+premise 完整）

组成（每次供给 attempt 输出一条旁证 + 关联标记）：
- `attempt`：{sessionId, turn, step, clProject, revision, msgId, content_sha256_12, outcome: appended};
- `acceptance`：{msgId, present_in_final_batch: bool}——按接纳定义写；
- premise 旁证**明确标注**记录的是"**瀑布入口的原始领取批次**"（当前实现即如此，字段名不改、语义在 note 中声明）；
- 派发事件照旧携带派生摘要（声明其可能滞后于领取批次）；
- 三者以 (sessionId, turn, step) 关联；**消息 ID 与内容指纹使"供给消息"可在任何一份记录中被独立识别**，不依赖 derived+premise 拼合假设。
- 提交级持久化（消息是否进入会话 v4 归档）：本轮**未验证**（需解压归档对账；标未验证）。

## 5. off 语义（显式区分）

- **off = 停止新的供给尝试**。已存在于会话历史中的供给消息**不被移除、不被改写**。
- 干净新会话 + off：可验证"无新增 CL 内容"（原阶段 1 off 证据继续有效）。
- **已有会话切 off**：历史中已有 CL 消息仍可见——本轮不提供、也不宣称提供"运行中清除"。
- off 不碰系统提示（本方案本就不使用系统提示）；**不改系统提示 ≠ 安全要求自动通过**——CL 数据不构成执行授权、不覆盖 DSH 安全审批的约束由消息内规则文本 + 本声明共同承载，其有效性属行为观察（本轮注入 run 中模型已正确执行"不因写入获得指令权限"，但该观察不外推为安全证明）。
