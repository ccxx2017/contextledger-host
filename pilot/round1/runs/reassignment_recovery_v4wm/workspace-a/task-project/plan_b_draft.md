## 1. 背景与动机

- 方案 A 交付后实测确认：Python 对象链（list→tuple→hash→ndarray）是
  数值管线的最大隐性开销；回测本体向量化收益 ~2.5x，而输入转换链
  占未命中路径耗时的主要部分。
- 本仓库当前只有冻结的 `backtest.py` 与其测试，**没有数据层**：
  数据加载、校验、供给均为空白。任何后续量化模块（因子、组合、新回测）
  都需要统一的数据入口。
- 方案 B 的定位：**把数据入口一次性做对**——全程 ndarray-native，
  数据只转换一次、校验一次、多方复用。

## 2. 目标与非目标

**目标**
1. 新建数据供给模块 `datafeed.py`：加载（CSV/内存序列）→ 校验 → 以
   `np.ndarray` 供给下游；
2. 校验契约显式化（NaN/inf/dtype/维度策略，会上拍板，避免重演方案 A 的
   NaN 语义遗留问题）；
3. 基准与测试齐备，质量门与方案 A 同标准（pytest / ruff / coverage）。

**非目标**
- 不改动 `backtest.py`（冻结约束，硬边界）；
- 不做数据库/网络数据源（首版只覆盖 CSV 与内存序列，扩展留接口）；
- 不做因子计算等上游业务逻辑。

## 3. 选型实测（2026-09-25，本机 Win / Py3.9 / numpy 2.0.2 / pandas 2.3.3）

CSV 加载 10 万行单列（1.1 MB）：

| 加载路径 | 耗时 | 折算每百万行 |
|---|---|---|
| `np.loadtxt` | 14.4 ms | ~144 ms |
| `np.genfromtxt` | 100.2 ms | ~1002 ms（**出局**） |
| `pandas.read_csv` + to_numpy | 14.2 ms | ~142 ms |

内存转换开销：10 万行 `list → np.asarray` ≈ 2.0 ms（即 ~20 ms/百万行），
数据层原生 ndarray 后此类转换在管线上只发生一次而非每次消费。

**选型建议**：loader 用 `pandas.read_csv`（多列 OHLCV、dtype 控制、NA 处理
开箱即用；单列小文件场景与 loadtxt 打平，规模/宽度上去后预期拉开——M3 基准复核）。

## 5. 设计草图（B1）

```
CSV 文件 ──┐
           ├─> datafeed.load_prices(source) ─> 校验 ─> np.ndarray (float64, 1d)
内存 list ─┘                                        （可选：load_ohlcv -> 2d + 列名）

校验契约（待上会拍板，默认值即建议值）：
- NaN：默认拒绝（ValueError），与方案 A 的"沿用基线"不同——数据层是新契约，
  建议从严；脏数据在入口拦截一次，而不是在每个消费方各自处理
- ±inf：默认拒绝（同上）
- dtype：非数值默认拒绝；int 序列升格 float64（与回测消费口径一致）
- 维度：一维；空序列：允许（返回空 ndarray），消费方自行决定语义
```

与冻结回测的对接：短期经适配函数 `as_sequence(arr)`（零拷贝视图即可满足
Sequence 读协议的路径优先），**明确标注**适配不产生额外收益；长期收益在
backtest 解冻后直吃 ndarray 兑现。数据层价值独立成立：加载/校验一次，
N 个消费方复用。
