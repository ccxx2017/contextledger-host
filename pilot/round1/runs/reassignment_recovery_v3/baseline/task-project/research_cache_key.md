# V2-5 预研：数据版本缓存 key（结论稿，只评估不实现）

> 对应 `plan_a_v2.md` V2-5。范围：仅评估与结论，不改 `run_backtest`
> 代码与对外契约。数据依据：notes.md「性能（v2 恢复后复测）」节。

## 1. 问题（v1 遗留项）
- 现状缓存 key = `tuple(prices)`：**命中路径**也要 O(n) 元组化 + O(n) 哈希。
- 复测实测（200k）：hit ≈ 6.0ms，其中 tuple 化 ≈ 0.9ms、按值哈希 ≈ 5ms，
  纯查找 + 结果构造 < 0.5ms——按值归一化占 hit 成本 > 90%。
- 长序列重复回测的缓存收益只剩常数项（hit 对基线 2.25x，无法逼近 O(1)）。

## 2. 备选方案
| 方案 | 设计 | 契约影响 | 评价 |
|------|------|----------|------|
| A | `run_backtest(prices, *, cache_key=None)`：提供 `cache_key` 时以其为缓存键，跳过按值归一化 | 向后兼容（可选关键字参数），返回结构不变 | 首选：模块内闭环，调用方按数据版本传 key |
| B | 独立 `BacktestCache` 门面对象：显式 `cache.run(prices, key)` | 零改动现有函数 | 备选：多数据集并行缓存场景 |
| C | 缓存整体上移出模块，调用方自管 | 模块回归纯函数（未来 major） | 若方案 B（数据层）启用则天然归位 |

**通用防线（A/B 均需）**：模块强制校验 `len(prices)` 与缓存记录一致；
契约文档醒目标注"调用方保证同 key 同数据"；建议调用方附加数据指纹。

## 3. 收益估算（以 200k 复测值推算）
- hit：6.0ms → **< 0.05ms**（消除 tuple 化 + 按值哈希），对基线加速
  由 2.25x → **三个数量级以上**；5k/50k 同比受益。
- miss 路径不受影响；小序列（n≤5k）hit 也从 ~13–125us 降至 ~1–2us。
- 适用前提：同一数据集多次回测/调参——正是量化主场景；一次性序列无收益。

## 4. 风险与对策
| 风险 | 对策 |
|------|------|
| 版本纪律失守 → 静默脏读（错结果比慢更糟） | len 强制校验 + 契约醒目 + 数据指纹建议；文档给反例 |
| API 面扩张 | 仅可选关键字参数 / 独立对象，不破坏现有调用 |
| 与方案 B 职责重叠 | key 结构直接对齐 plan_b 建议 `(数据集版本, 标的集 hash, 区间)`；B 启动则并轨 C |

## 5. 结论与建议
1. **值得做**：长序列重复回测收益显著且实现面小。
2. 首选**方案 A**（向后兼容、模块内闭环）；B 为多数据集场景备选；
   方案 B 启动则并轨 C，key 设计复用其三元组。
3. **本阶段（v2）不实现**。实现排入 v2.x/v3，沿用方案 A 方法论：
   契约先行 → 等价性 fuzz 扩展（新增 key 命中一致性用例：
   同 key 跨调用结果一致、len 防线触发路径）→ 覆盖 Gate → 基准复测。
